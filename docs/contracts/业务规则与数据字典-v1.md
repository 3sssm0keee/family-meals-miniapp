# 业务规则与数据字典 V1

状态：开发契约，未实现。与 openapi-v1.json 配套使用，替代 v0.1 提纲。本版对缺失的非关键细节作明确默认选择，不将默认项冒充用户已确认项。实现若发现必须改变合同，先修改本套契约和版本，再同步前端。

## 1. 范围和确认边界

用户已确认：一个小程序；东八区；中饭/晚饭；管理员按菜品版本查看参与情况；同版本人数与制作份数分离；确认后新增需求待审核；24 小时邀请码多人使用、每人兑换一次；保留历史快照；管理员确认结果才发送通知。后续修复要求菜品及规格原记录物理删除，覆盖本版原软删除约定。

V1 默认确定：

- ADMIN 具备成员能力及全部家庭管理能力；MEMBER/GUEST 均能选择、提交、查看公共菜单，但没有参与名单、他人备注和管理接口权限。
- 邀请可授予 MEMBER/GUEST，前端初始选 GUEST；不能通过邀请码授予 ADMIN。邀请 24 小时到期不自动移除已加入成员。
- 每家庭每天两餐，每人每餐一份个人菜单：首次非空提交后，当天可追加新版本；同版本只选一次，可以同时选不同版本。不可删除既有条目，整体备注通过独立接口修改。
- 成员选择不含数量；管理员填写 0.1～999.9 份，一位小数；每版本 portionDescription 必须说明一份规格。
- 当天可提交、改备注、编辑购物车、审核及新建临时菜；历史只读。服务器按 Asia/Shanghai 判定当天，不信任客户端日期。提前点餐、餐次截止、菜谱营养计算、支付和配送不在 V1。
- 保留近六个自然月菜单；客户端可选日期为当前东八区日期减六个日历月至当天，月底按目标月最后一天截断。V1 实现先不自动清理历史数据库；任何真实清理另行处理。超出查询窗口返回 400。
- 版本最多 20 个；每次个人选择、单次审核最多 100 项；家庭实际人数和菜品量是设计规模，不作为未经说明的硬性注册限制。
- 新用户后端产生“家庭成员”默认显示名，可在资料页面修改。允许同名，所有计数和权限按 ID。
- 管理员可以安排零人选择的临时菜；正式菜需有成员需求才进入菜单，额外安排用临时菜入口。

## 2. 权限矩阵

| 行为 | 未登录 | 已登录未加入 | GUEST/MEMBER | ADMIN |
| --- | --- | --- | --- | --- |
| 微信登录 | 是 | 是 | 是 | 是 |
| 个人资料/自己的家庭列表/创建家庭/兑换邀请 | 否 | 是 | 是 | 是 |
| 本家庭菜品、图片及公共菜单 | 否 | 否 | 是 | 是 |
| 自己的购物车/提交/备注/通知记录 | 否 | 否 | 是 | 是 |
| 全部参与名单与备注 | 否 | 否 | 否 | 是 |
| 菜品、文件上传、临时菜、审核、邀请、成员管理、审计 | 否 | 否 | 否 | 是 |

JWT 有效期 2 小时；仅载用户身份、签发与过期信息，角色以实时成员关系为准。无 refresh token；401 后通过 wx.login 获取新 code 再登录。微信 app secret 和 openid 不返回前端。

familyId 是选择上下文，不是授权凭证。后端在事务/操作时校验 ACTIVE 成员及角色；资源查询同时匹配 familyId 与资源 ID。通过 body 注入 familyId/userId/role 等未声明字段返回 400。文件绑定也必须验证家庭归属。

跨家庭资源返回 404；不属于路径家庭返回 403。管理员降级、移除与业务写入并发时，写入事务必须重新确认成员资格，不能只依赖请求开始时的 Guard 结果。

## 3. 登录、家庭与邀请码

1. 登录成功持久化 token 和 expiresAt；默认从 /me/families 选择家庭。无家庭显示“创建家庭/加入家庭”，不伪造家庭 ID。
2. 创建家庭事务创建 ACTIVE ADMIN；family_member(family_id,user_id) 唯一。家庭始终至少一位 ACTIVE ADMIN，移除/退出/降级最后管理员返回 LAST_ADMIN。
3. 邀请码使用至少 128 位随机熵的 URL-safe 字符串（API 字符长度至少 32）。数据库存 SHA-256 摘要；明文仅首次创建及同幂等键重放返回。为支持重放，幂等响应中的邀请码需加密保存，不写日志。
4. expiresAt = createdAt + 24h；now >= expiresAt 为过期。邀请码列表不返回明文。撤销只影响后续加入。
5. 已兑换且仍 ACTIVE：再次兑换同码返回成功 alreadyJoined=true，即使后来过期或撤销。已退出/被移除：同码返回 INVITE_ALREADY_USED；新有效码可以重新激活原成员记录。已 ACTIVE 的用户兑换另一个有效码不更改原角色，记录该次兑换，返回 alreadyJoined=true。
6. 未兑换者先校验码有效性再建立/激活成员，使用事务和唯一约束防止并发重复。错误码不泄露其他家庭的资料。

## 4. 餐次、购物车及提交

- GET /meal-sessions 只查询已有餐次，无记录返回 []。POST /meal-sessions 对当天餐次 get-or-create，返回 200 同一个 ID，不重复建餐次。
- Session.reviewVersion 初始 1。Session.canSubmit 由服务端计算：当天且本人未提交。成员资格不足直接返回 403；已提交优先返回 ALREADY_SUBMITTED，否则历史返回 DATE_READ_ONLY。
- 购物车每成员每餐一个逻辑集合，version 初始 1。首次读取无内容返回 version=1,items=[]；添加已有项、删除不存在项不增加 version，实际变更才加 1。
- 购物车是辅助选择记录。POST personal-menu 中 variantIds 是最终完整选择；后端在事务中重验家庭、餐次、菜品与版本有效性，不把购物车瞬时内容当成提交正文。
- 购物车添加/删除与提交对同一成员餐次串行化。当天提交后购物车仍可用于追加；首次提交成功清空购物车并更新其版本，追加只清理请求包含的购物车项。
- 正式或当餐临时版本才可提交；失效项返回 VARIANT_UNAVAILABLE，details.fieldErrors 标明对应 variantIds 下标，整个提交不部分成功。
- 每人每餐 PersonalMenu 唯一。相同幂等键重复返回原 201 和原结果；不同键再次提交返回 409 ALREADY_SUBMITTED，details.resourceId 返回本人的已有提交 ID。
- 成功事务包括个人菜单、快照条目、需求聚合项、餐次版本、幂等结果。数据库持久化成功才返回“提交成功”。不发送管理员确认通知。
- 未提交读取个人菜单返回 data:null。原有提交条目不可删除；POST personal-menu/items 携带 variantIds 增量与 expectedVersion 追加，仅当天已有提交可用（Session.canAppend）。保留个人菜单 ID、首次提交时间、备注及原有快照；新项重验可用性，累计最多100项。已有版本不重复计数，全部已存在则无变化。成功追加使个人菜单及餐次版本各加1，仅新增需求待审核；旧审批版本冲突。修改备注必须带 PersonalMenu.version，同内容无操作，不触发重审。

## 5. 汇总、快照和管理员审核

每个版本人数是该餐已提交且选择该版本的 memberId 去重数。菜品人数是所有版本参与者的并集大小。成员后续退出不回删已经提交的选择；管理员可以据此调整制作安排。参与名单使用当前显示名（成员记录保留），菜名/版本名/规格使用菜单项快照。

FamilyMenuItem 在某版本第一次提交时创建快照；后续提交同一版本沿用该餐首份菜单项快照，确保同一审核卡片不出现多个名称。PersonalMenuItem 同样复制该餐快照。编辑菜品不改写既有餐次快照；新版资料用于新餐次。临时菜创建时即建立每版本的零需求快照项。

| 事件 | decision | plannedQuantity | needsReview | 版本变化 |
| --- | --- | --- | --- | --- |
| 首次需求或新增临时菜项 | UNREVIEWED | null | true | demandVersion=1，餐次+1 |
| 管理员确认 | CONFIRMED | 请求份数 | false | reviewedDemandVersion=demandVersion，餐次+1 |
| 管理员取消 | CANCELLED | null | false | reviewedDemandVersion=demandVersion，餐次+1 |
| 同版本新增参与者 | 保留 | 保留 | true | demandVersion+1，餐次+1 |
| 参与者备注变化 | 保留 | 保留 | true | 该参与者所选各项 demandVersion+1，餐次总共+1 |
| 重新确认/取消 | 新决定 | 新值 | false | reviewedDemandVersion 更新，餐次+1 |

needsReview = decision 为 UNREVIEWED 或 demandVersion > reviewedDemandVersion。lastReviewedParticipantCount 记录上次审核的人数，不替代当前人数。未审核时初始 0。

提交一次即使含多个版本，餐次 reviewVersion 只加 1。一次审核批次即使含多个项目也只加 1。行 demandVersion 只因需求或备注改变增加，管理员操作不改变需求版本。

审核携带 expectedReviewVersion，后端锁定餐次、检查版本和权限，所有 itemId 必须唯一且属于该餐。任一错误全部回滚。返回 409 REVIEW_VERSION_CONFLICT 和 currentVersion 时，前端保留本地草稿、拉新视图、让管理员重新核对，不能自动盲重试。

取消原因必填，确认原因可以空字符串；CONFIRMED 份数正数，CANCELLED 份数严格 null。未选中项保持不变。完全无变化且无需重审的重复决定返回 400 VALIDATION_ERROR；旧键重试仍返回原结果。审核后生成不可变批次快照与通知记录，并返回完整新审核视图。

## 6. 菜品、版本、临时菜、文件

- 菜品和版本的 name 去首尾空白后不得为空；所有文本禁止 HTML 解释，按纯文本显示。未知字段拒绝。可空字段必须显式 null；PATCH 省略表示保留，空字符串只对允许空的说明字段有效。
- 同家庭当前正式菜名不区分大小写唯一；同菜品未删除规格名同样唯一。临时菜名按 originSessionId 限定唯一。返回 DUPLICATE_NAME。已物理删除菜品及软删除规格不占用名称。
- 菜品 PATCH/DELETE、版本 PATCH/DELETE、转正式使用 expectedVersion，版本不符返回 VERSION_CONFLICT 和 currentVersion。创建/修改/删除版本同时使父菜品 version+1，事务中防止父菜品编辑覆盖。
- 菜品删除在事务内物理删除其所有规格原记录，移除对应未提交购物车项并递增受影响购物车版本；已提交点单与家庭菜单保留原 ID 和名称、份量、备注及审核结果快照。历史菜名、规格名或份量快照为空或仅含空白时阻止删除。关闭或软删除的规格不能新加入购物车/提交，旧提交仍可审核；单独删除规格时不能删除最后一个未删除规格（400）。
- 临时菜与正式菜共用模型。转正式需未删除、kind=TEMPORARY，保留 ID/originSessionId，校验正式菜重名。未来餐次可使用；过去快照不变。已正式使用新键再次迁移返回 TEMPORARY_ONLY。
- 图片上传通过 multipart file，5 MiB=5,242,880 字节上限；允许真实 JPEG/PNG/WebP，服务端检测格式并剥离 EXIF。签名地址 15 分钟有效，前端存 fileId 而非永久缓存 URL。跨家庭 fileId 禁止绑定；非管理员仅能读取已关联可见菜品图片。
- V1 不做用户自行删除文件接口；未绑定文件的回收由后端运维另行设置，不作为前端依赖。

## 7. 幂等、错误、分页和时间

- 除登录外所有写操作必须带 Idempotency-Key：16～128 位字母、数字、下划线或连字符；建议客户端 UUID。失败后的人工修正使用新键；网络不明时保持原键和原正文。
- 幂等作用域为 userId + familyId（全局为 null）+ HTTP 方法 + 规范路径 + key。正文和 query（删除版本参数也包括）规范化计算 SHA-256，文件按实际字节摘要。
- 原子保留 key，执行中返回 409 REQUEST_IN_PROGRESS；同键不同请求返回 409 IDEMPOTENCY_CONFLICT。已提交结果保存 24h，重放原状态码及业务响应；新的 requestId 可重新产生。回滚/验证失败不持久保存成功记录。
- 重放时仍验证 JWT 和权限，防止管理员降级后读取敏感响应。唯一例外：本人退出/移除自身导致失去关系时，原 key 仅允许重放 ok:true，不能读取其他家庭数据。数据库永久唯一约束继续保护个人提交和邀请码，不依赖 24h 缓存。
- 401：清理旧 token，重新登录。403：刷新家庭列表并退出失去权限的页面。404：显示资源不存在并刷新列表。409：按 code 分流；审核/数据版本冲突必须核对。410：邀请码失效。413/415：要求换图片。429：按 Retry-After 秒数等待。500/503：显示失败，保留草稿。
- requestId 用于排查，不将数据库错误或凭据放入 message/details。ErrorDetails 未适用字段省略，空对象合法。
- 列表默认 createdAt DESC,id DESC 稳定排序；成员按 joinedAt DESC,id DESC。page 默认1，pageSize 默认20最大100，越界页返回空 items 和真实 total。
- 公共菜单按菜品快照名、dishId，版本按快照名、variantId 排序；参与者按 submittedAt、memberId 排序。
- 时间戳均 UTC Z；显示转东八区。业务日期无时分。服务端返回 serverTime，午夜切日后旧页写操作返回 DATE_READ_ONLY。

## 8. 通知

- 小程序先读 notification-config；enabled=false 时不弹订阅请求。enabled=true 时使用 templateId 调用微信订阅能力，将结果提交 subscription-results。客户端结果只作意愿记录，不能证明平台授权。
- 管理员审核事务保存批次完整菜单快照及通知记录；接收者为该餐所有已提交且仍 ACTIVE 的成员，每批次每成员最多一条。管理员自己若提交也在内。无人提交则通知记录为 0。
- 批次保存已选审核变更和确认后的完整菜单；发送正文明确餐次和管理员结果，不描述为用户提交回执。缺少授权/渠道配置仍记录 SKIPPED，方便区分未发送与发送成功。
- 后台读取数据库待发送记录，不引入 Redis/消息队列。明确可重试错误最多3次，间隔1分钟、5分钟、15分钟；达到上限 FAILED。供应商明确成功 SENT；传输超时且无法确认送达记 UNKNOWN，不盲目自动重发。
- PENDING 可转 SENT/FAILED/SKIPPED/UNKNOWN；终态不自动回到 PENDING。通知失败不回滚菜单结果。Notification UNKNOWN 是对 v0.1 的补充，避免将不确定送达假报为失败。
- 用户前端不需要公开轮询全部成员发送状态，只能查看自己的通知记录。未接入真实微信配置前 enabled=false，不伪造成功。

## 9. 数据字典

数据库为 MySQL 8，snake_case；API 为 camelCase。所有 id 是 VARCHAR(64) 主键；时间用 UTC DATETIME(3)；文本 utf8mb4；说明字段 NOT NULL 默认空字符串，明确标“可空”除外。所有表默认含 created_at、updated_at。以下列出完整业务字段；真实 Prisma 迁移由后端实现，不交由前端执行。

| --- | --- | --- |
| users | id；wechat_app_id VARCHAR(64)；openid VARCHAR(128)；display_name VARCHAR(40) | UNIQUE(wechat_app_id,openid)；openid 不出 API |

active_name_key：正式菜为 P:normalizedName；临时菜为 T:sessionId:normalizedName；删除后为 null。版本为 normalizedName，删除后为 null。大小写规则由后端规范化统一。dish.name 改动同步 active_name_key，数据库唯一约束作为并发最后防线。

所有家庭业务表的外键优先以 (family_id,resource_id) 复合引用，禁止仅按裸 ID 关联。无复合唯一键的子表不作为跨表父资源。已提交点单与家庭菜单保留原菜品/规格 ID 标量和业务快照，但不再对实时菜谱建立外键；其他关联仍使用 RESTRICT。物理删除菜谱不得级联删除历史。后台 worker 同样按 family_id 读取，不能绕过隔离。

## 10. 接口兼容与交付状态

openapi-v1.json 是字段和路由的唯一机器契约；本文件是事务与权限语义依据。frontend-types.ts 由契约生成，不手工改。examples-v1.json 提供按 operationId 索引的样例，不是实际服务数据。

本版新增了 v0.1 未列的管理菜品查询、用户资料、餐次创建、图片刷新、通知配置/意愿记录、审计查询等前端必要接口。v0.1 的隐式 GET 创建餐次改成显式 POST。

环境 URL、微信 AppID/模板 ID、测试账号不虚构，后端就绪后另交环境配置。缺少这些不会影响契约驱动页面开发，但真实联调必须等待真实环境。静态契约校验不能证明后端业务、数据库事务或微信消息已运行。
